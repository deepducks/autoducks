The Tactical agent reads a designed feature issue and produces a tactical plan: numbered task issues with acceptance criteria, a YAML wave structure, and a feature branch. It turns "here's the spec" into "here's exactly what to build, in what order."

**Type:** LLM (Claude)  
**Script:** `.autoducks/agents/tactical/pre.sh` + `post.sh`

## Triggers

| Event | Condition |
|-------|-----------|
| Issue comment | `/agents devise` |
| Issue comment | `/agents execute` on a `Feature` issue **without** the `Ready` label (auto-escalation) |

## Behavior

<details>
<summary>Pre-execution</summary>

1. Reacts to the trigger comment with 👀.
2. Fetches the issue content and writes it to `/tmp/issue-request.md`.
3. **Revision detection:** if the issue already has the `Ready` label, this is a plan revision. The agent extracts existing task numbers from the YAML block and builds revision context (prior plan + recent comments).
4. Adds `Tactics:crafting` to the issue to indicate that tactical planning is in progress.

</details>

<details>
<summary>LLM execution</summary>

The agent reads the issue spec (and revision context if applicable) and produces:

**Option A — a tactical zone** written to `/tmp/tactical-body.md`, containing only the tactical content (no design summary). Structure:
```markdown
## Plan

```yaml
waves:
  - name: Wave 1
    tasks: [T1]
```

## Tasks

### T1 — Title `priority:P0`

**Summary:** What this task does.

**Tasks:**
- [ ] Specific implementation step

**Acceptance Criteria:**
- [ ] Testable criterion

## Progress

- [ ] #T1 Title `P0`

## Notes

Optional tactical caveats (design spec is NOT re-summarized here).
```

**Option B — questions** written to `/tmp/questions.md` if critical information is missing to produce a good plan.

</details>

<details>
<summary>Post-execution</summary>

5. **Questions mode:** posts questions as a comment and exits (waits for human clarification).
6. **Parse the tactical body:** `parse-plan.py` extracts tasks from the `## Tasks` section, validates structure, and produces `/tmp/tasks.jsonl`. On parse failure: posts error as comment and exits.
7. **Reconcile tasks:** creates new task issues, updates existing ones if changed, closes dropped tasks. Maps `T1`/`T2` placeholders to real issue numbers.
8. Replaces `T1`/`T2` placeholders with real issue numbers. Strips the `## Tasks` section (tasks are now separate issues). Assembles the final body by merging the design zone with the new tactical zone (separated by sentinel markers). Updates the feature issue body.
9. **First pass only** (not revision): removes `Tactics:crafting` and adds `Tactics:ready` (planning complete) and `Ready` (execution routing signal). `Tactics:ready` and `Ready` coexist — `Tactics:ready` records that planning finished; `Ready` is the signal the Wave Orchestrator checks to route execution. Also sets issue type to `Feature`, creates feature branch `feature/{id}-{slug}`, creates a draft PR targeting `main`, assigns the commenter.
10. Reacts with 👍 and posts a comment listing created tasks with a suggestion to run `/agents execute`.

</details>

## Output

- **Task issues created** as children of the feature issue, each with type `Task`
- **Feature issue body updated** with wave structure (YAML block) and task references
- **`Tactics:crafting` removed; `Tactics:ready` added** — tactical phase complete
- **`Ready` label added** to the feature issue (execution routing signal; coexists with `Tactics:ready`)
- **Feature branch created:** `feature/{id}-{slug}`
- **Draft PR created** targeting `main` (first pass only)

## Issue body zones

After the first `/agents devise` run, the feature issue body is split into two zones separated by HTML-comment sentinels (invisible in rendered Markdown):

```
<!-- autoducks:tactical:begin -->
...tactical zone content...
<!-- autoducks:tactical:end -->
```

| Zone | Owned by | Content |
|------|----------|---------|
| **Design zone** — everything *above* the begin marker | Design Agent / humans | Problem statement, proposed solution, technical design, constraints, out-of-scope |
| **Tactical zone** — content *between* the markers | Tactical Agent | `## Plan` (YAML waves), `## Progress` (task checkboxes), `## Notes` |

The Tactical Agent **never rewrites the design zone**. On each `/agents devise` run it reads the design zone as read-only context and only updates the tactical zone.

<Aside type="caution">
If you manually remove or misplace the sentinel markers, the next `/agents devise` run will fail loudly with a `confused` reaction rather than silently overwriting your edits. Keep both markers intact.
</Aside>

<Aside>
If you paste a snippet that duplicates the markers, the agent takes the first `begin` and the first `end` after it on the next revision. Any content after the first `end` marker is discarded. This is a known limitation.
</Aside>

## Wave structure

The tactical plan embeds a YAML block in the feature issue body that the Wave Orchestrator uses:

```yaml
waves:
  - tasks: [101, 102]       # Wave 1: parallel tasks
  - tasks: [103]            # Wave 2: depends on Wave 1
  - tasks: [104, 105]       # Wave 3: depends on Wave 2
```

Tasks in the same wave run in parallel. Each wave starts only after the previous wave is fully done (all task PRs merged).

## Native sub-issue linking

Every task issue is linked to its parent Feature via GitHub's native
sub-issues relationship (visible as a "Sub-issues" panel and progress bar
on the Feature, and a "Parent issue" link on each Task).

The linkage is created by `its::link_sub_issue` inside the Tactical agent's
reconcile step, immediately after each task issue is created (or, on
revision, after each existing task is re-verified). The behavior is:

| Repository state | Outcome | Reported in completion comment |
|-------------------|---------|--------------------------------|
| Sub-issues API available, token has `issues:write` | Every task linked | "All tasks linked as native sub-issues" |
| Sub-issues API unavailable (feature disabled) | Nothing linked; markdown checklist is the source of truth | "Native sub-issue linking is not available for this repository" |
| Token missing `issues:write` | Nothing linked | "Native sub-issue linking was refused" |
| Partial failure (e.g. GitHub outage) | Whatever tasks were linked stay linked; the rest are retried on next `/agents devise` | Explicit count and per-category breakdown |

The `## Progress` checklist inside the tactical zone remains the source of
truth for wave parsing and the Wave Orchestrator. Native sub-issue linking
is a visual layer, not a control-plane substitute — the same relationship
autoducks currently maintains via label + parent-issue reference.

<Aside>
The Tactical agent probes the API once per run and caches the result. If
you enable the sub-issues API mid-project (or your token gains
`issues:write`), the first `/agents devise` after the change reconciles
every task, including previously created ones that had no native link.
</Aside>

## Required permissions

```yaml
permissions:
  contents: write
  issues: write
  pull-requests: write
  id-token: write
```

## Directive arguments

```
/agents devise --model claude-opus-4-7
```

| Argument | Default | Description |
|----------|---------|-------------|
| `--model` | From `.autoducks/autoducks.json` | Claude model to use |
| `--reasoning` | From `.autoducks/autoducks.json` | Reasoning effort |

<Aside type="caution">
Running `/agents devise` on an issue that already has `Ready` triggers **revision mode**. Existing tasks that are already completed (have a merged PR) will not be touched. Dropped tasks will be closed with a comment.
</Aside>
