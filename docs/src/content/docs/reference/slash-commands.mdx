All autoducks commands are issued as issue comments using the `/agents` prefix.

## Command overview

| Command | Issue type | Label required | What it triggers |
|---------|-----------|----------------|-----------------|
| `/agents design` | Any | — | [Design agent](/agents/design) |
| `/agents devise` | Any | — | [Tactical agent](/agents/tactical) |
| `/agents execute` | Feature | `Ready` | [Wave Orchestrator](/agents/wave-orchestrator) |
| `/agents execute` | Feature | — (no `Ready`) | Tactical agent (auto-escalation) |
| `/agents execute` | Non-Feature | — | [Execution agent](/agents/execution) |
| `/agents fix` | Any | — | [Fix agent](/agents/fix) |
| `/agents revert` | Feature | — | [Revert agent](/agents/revert) |
| `/agents close` | Feature | — | [Close agent](/agents/close) |

> **"Feature" routing note:** In the table above, "Feature" refers to either the native GitHub issue type *or* the `Feature` label — whichever applies. On user-owned (personal) repositories, native issue types are not available, so the `Feature` label is the sole routing signal. The tactical and design agents apply this label automatically; no manual labeling is required.

## Built-in aliases

Every installation ships with synonym verbs that resolve to the canonical
command. They behave identically to the canonical verb — including
`/agents execute` auto-escalation — and require no configuration.

| Canonical verb | Built-in aliases |
|----------------|------------------|
| `design` | `plan` |
| `devise` | `drilldown`, `specify` |
| `execute` | `work`, `run`, `start` |
| `fix` | _(none)_ |
| `revert` | _(none)_ |
| `close` | _(none)_ |

For example, `/agents plan` is equivalent to `/agents design`, and
`/agents work` on a Feature + `Ready` issue triggers the Wave Orchestrator just
like `/agents execute`.

## Custom aliases

Teams can register their own alias verbs per agent in
`.autoducks/autoducks.json` under the `triggers` key. Because GitHub Actions
evaluates workflow `if:` guards without reading repository files, custom aliases
must be **baked into the workflow YAML at setup time** and the regenerated
workflows committed. See the
[configuration reference](/reference/configuration#custom-trigger-aliases) for
the schema, validation rules, and the `update-triggers` command.

## Directive arguments

All commands accept optional inline arguments:

```
/agents <command> [--model <model>] [--reasoning <level>] [turns=<n>]
```

### `--model`

Override the Claude model for this run. Accepts any valid Claude model ID.

```
/agents design --model claude-opus-4-7
/agents execute --model claude-haiku-4-5-20251001
```

Default: value from `.autoducks/autoducks.json` → `defaults.model`

### `--reasoning`

Override the reasoning effort level.

| Value | Description |
|-------|-------------|
| `low` | Faster, less thorough |
| `medium` | Balanced |
| `high` | Slower, more thorough (default) |

```
/agents devise --reasoning medium
```

### `turns=<n>`

Override the maximum number of agentic turns for this run. Unlike `--model` and `--reasoning`, this is a **positional** token, not a `--flag` — drop it anywhere after the command verb, alongside model/reasoning aliases:

```
/agents execute sonnet high turns=80
```

`max-turns=<n>`, `max_turns=<n>`, and `turns:<n>` are accepted as equivalent forms. `<n>` must be a positive integer no greater than 1000; a malformed or out-of-range value is ignored rather than rejected, leaving the override empty so the next tier applies.

This directive is parsed by the same comment parser everywhere, so `turns=<n>` propagates through the wave path too: on a Feature issue, the Wave Orchestrator picks it up from the triggering comment just like it does for `--model`/`--reasoning`.

**Priority (highest to lowest):** inline `turns=<n>` directive → per-agent `defaults.json` → global `.autoducks/autoducks.json` → provider action default.

Default: `50`, applied by the Claude provider action when `max_turns` is unset at every tier above — see [`defaults.max_turns`](/reference/configuration#defaultsmax_turns).

## Pipeline shortcut

If you comment `/agents execute` on a Feature issue that doesn't have the `Ready` label yet, autoducks will **auto-escalate** to the Tactical agent first, then proceed to execution. This lets you use a single command for the full pipeline without worrying about which step you're at.

If the issue also lacks a design spec (just a raw idea), comment `/agents design` first to get a proper spec before planning.

## Programmatic dispatch

The Wave Orchestrator and Execution agents can also be triggered programmatically — bypassing the issue comment trigger entirely. How this is done depends on the runtime.

**GitHub Actions runtime** (using the `gh` CLI):

```bash
# Trigger the wave orchestrator for a feature issue
gh workflow run autoducks-wave.yml -f feature_issue=42

# Trigger an execution agent directly
gh workflow run autoducks-execute.yml -f issue_number=43 -f base_branch=feature/42-my-feature
```

Other runtimes expose this through their own workflow/pipeline trigger mechanism.
