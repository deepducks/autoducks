autoducks is configured via `.autoducks/autoducks.json` at the root of your repository.

## Full schema

```json
{
  "providers": {
    "its": "github",
    "git": "github",
    "llm": "claude"
  },
  "defaults": {
    "model": "claude-sonnet-4-6",
    "reasoning": "high",
    "max_turns": 50,
    "base_branch": "main",
    "integration_branch": "main",
    "merge_method": "auto"
  }
}
```

<Aside type="note">
`integration_branch` is optional — omit it unless you need the fork workflow described below.
</Aside>

## `providers`

Selects the implementation for each of the three provider interfaces.

### `providers.its`

Issue Tracking System provider. Controls all issue tracker interactions: issue creation/update, labels, comments, PR management, reactions.

| Value | Status | Description |
|-------|--------|-------------|
| `github` | ✅ Supported | GitHub Issues via the `gh` CLI |

### `providers.git`

Git operations provider. Controls: branch creation/deletion, commits, pushes, PR merge.

| Value | Status | Description |
|-------|--------|-------------|
| `github` | ✅ Supported | Git CLI with GitHub repository operations |

### `providers.llm`

LLM provider. Controls: design spec generation, tactical planning, code execution, fix attempts.

| Value | Status | Description |
|-------|--------|-------------|
| `claude` | ✅ Supported | Anthropic Claude via the Claude Code action |

## `defaults`

Default runtime parameters used by all agents unless overridden by a [directive argument](/reference/slash-commands#directive-arguments).

### `defaults.model`

The Claude model ID to use for LLM agents.

**Default:** `claude-sonnet-4-6`

Recommended values:

| Model | Use case |
|-------|----------|
| `claude-sonnet-4-6` | Default — good balance of speed and quality |
| `claude-opus-4-7` | Best quality for complex design/tactical work |
| `claude-haiku-4-5-20251001` | Fastest, lowest cost — good for simple execution tasks |

### `defaults.reasoning`

Reasoning effort level for LLM agents.

| Value | Description |
|-------|-------------|
| `low` | Faster, less thorough |
| `medium` | Balanced |
| `high` | Slower, more thorough (default) |

### `defaults.max_turns`

Maximum number of agentic turns an LLM agent may take before its run is stopped.

**Default:** `50`

Unlike `model` and `reasoning`, this key has no baked-in value in `defaults` — it's optional at every config layer. If it's omitted from the global config, the per-agent `defaults.json`, *and* the inline directive, the Claude provider action itself falls back to `50`.

### `defaults.base_branch`

The **cut-point**: the branch that feature branches and orphan task branches are created from.

**Default:** `main`

When `defaults.integration_branch` is unset, `base_branch` also serves as the PR target — the branch that feature PRs and orphan task PRs are opened into. Once `integration_branch` is set, it takes over the PR-target role and `base_branch` remains only the cut-point.

<Aside type="note">
The `base_branch` default can be overridden at runtime via the `BASE_BRANCH` environment variable passed to workflow dispatch. The wave orchestrator always reads this from the feature branch name.
</Aside>

### `defaults.integration_branch`

The **PR target**: the branch that feature PRs and orphan task PRs are opened into.

**Default:** `base_branch` (unset by default — no separate integration branch)

This exists to support a **fork workflow**, where `base_branch` is the upstream cut-point but PRs should land on a fork-local integration branch instead of going straight upstream. Setting `integration_branch` requires no migration: leave it unset and behavior is unchanged (PRs continue to target `base_branch`).

The following invariant always holds:

```
merge-base(feature/<slug>, integration_branch) == base_branch
```

That is, no matter where a feature or task branch is cut from (`base_branch`), its PR always resolves cleanly against `integration_branch` because the two share a common ancestor at `base_branch`.

### `defaults.merge_method`

The method used when agents auto-merge a task or fix PR into its feature branch.

**Default:** `auto`

| Value | Description |
|-------|-------------|
| `auto` | Detect an allowed method from the repository settings, preferring `merge` → `squash` → `rebase` (default) |
| `merge` | Always create a merge commit |
| `squash` | Always squash-merge |
| `rebase` | Always rebase-merge |

<Aside type="note">
GitHub rejects a merge whose method the repository disallows (`HTTP 405 — Merge commits are not allowed on this repository`). Leaving this at `auto` keeps autoducks working on any repo regardless of which merge methods are enabled — including squash-only or rebase-only repos — without forking configuration. Pin a specific value only when you want to force one method.
</Aside>

## Per-agent defaults

Each agent can also have its own `defaults.json` in `.autoducks/agents/{agent}/defaults.json`:

```json
{
  "model": "claude-sonnet-4-6",
  "reasoning": "high",
  "max_turns": 50
}
```

Agent-level defaults override the global defaults. Directive arguments in slash commands override agent-level defaults.

**Priority (highest to lowest):**
1. Directive argument in comment (`--model`, `--reasoning`, `turns=<n>`)
2. Agent-level `defaults.json`
3. Global `.autoducks/autoducks.json`
4. Provider action default — applies only to `max_turns` (`50`), since `model` and `reasoning` always have a value by the time they reach step 3

Omitting `max_turns` from every layer above still yields a working run: it just resolves to the provider action's default of `50`.

## Security

autoducks gates every trigger through the [Authorization Gate](/reference/security) before any agent runs. The `security` block in `.autoducks/autoducks.json` controls who is allowed to trigger which agents — trusted GitHub author associations, per-agent overrides, and optional CODEOWNERS integration.

See the [Security reference](/reference/security) for the full threat model, config schema, and testing instructions.
